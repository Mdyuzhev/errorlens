# alembic/ — правила работы с миграциями

## Соглашение об именовании

Формат: `el0NN_краткое_описание.py`
Текущий последний файл: **el062_add_testrun_launch_fields.py**
Следующий номер: **el063**

Старые миграции с хеш-префиксом (`43fb843e4a0f_...`) — legacy, не трогать.

## Обязательные правила

Каждое изменение схемы = отдельный файл миграции. Никогда не редактировать
уже применённые миграции — это сломает цепочку `down_revision` на сервере.

## Подключение к БД

`alembic.ini` содержит placeholder URL. Реальный URL берётся из переменной
окружения `DATABASE_URL` в `env.py` (автоматически конвертирует `asyncpg` → sync driver).
Для локального запуска установить `DATABASE_URL` или использовать `.env`.

## Как создать миграцию

```bash
cd backend

# Автогенерация из изменений моделей (предпочтительно):
alembic revision --autogenerate -m "el047_add_something"

# Или вручную (если автогенерация не справляется):
alembic revision -m "el047_add_something"
```

После генерации — обязательно проверить созданный файл:
- `down_revision` указывает на `el046_add_testcase_linked_articles` (или текущий последний)
- `upgrade()` делает ровно то что нужно, не больше
- `downgrade()` корректно откатывает изменение

## Применение на сервере

```python
run_db_migration("errorlens", dry_run=True)  # Проверить что будет применено
run_db_migration("errorlens")                 # Применить
```

## Локальная проверка

```bash
alembic check          # Проверить что нет неприменённых изменений в моделях
alembic upgrade head   # Применить все миграции
alembic downgrade -1   # Откатить последнюю (для проверки downgrade)
alembic upgrade head   # Снова применить
```

## Если autogenerate создал лишнее

Алембик иногда видит изменения которые уже применены. Перед коммитом
всегда проверять содержимое сгенерированного файла вручную.

## Запрещено

- Редактировать уже применённые (`el001`–`el046`) миграции
- Несколько изменений схемы в одном файле миграции
- Оставлять неприменённые миграции при деплое
- Переименовывать файлы после их применения
